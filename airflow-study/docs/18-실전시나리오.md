# 18. 실전 시나리오

학습한 내용을 합쳐서 자주 마주치는 운영 상황별 절차로 정리합니다.

## 시나리오 1: 단일 Task가 일시적 장애로 실패

**상황**: 어제 새벽 DB가 잠시 끊겨 `extract` Task가 실패. 코드는 그대로 두고 다시 시도하고 싶다.

### 절차

1. UI → DAG 상세 → **Grid View**
2. 빨간 셀(`extract`) 클릭
3. 우측 패널 → **Logs**로 실패 원인 확인 (DB connection refused 등)
4. 우측 패널 → **Clear** 클릭
5. **Downstream**만 체크 (extract 이후도 함께 다시 실행)
6. Confirm → Scheduler가 자동으로 다시 큐잉

```
[Clear 모달]
[ ] Past
[ ] Future
[ ] Upstream
[●] Downstream      ← extract 다시 돌면 그 후도 다시
[ ] Recursive
[ ] Failed
        [ Cancel ]  [ Clear ]
```

📷 캡처 권장: `docs/images/18-01-clear-modal.png`

## 시나리오 2: 코드 수정 후 어제 DAGRun 재실행

**상황**: SQL의 버그를 발견. 어제 logical_date(2026-01-03)의 결과를 새 코드로 다시 계산하고 싶다.

### 절차

1. 코드 수정 → 30초 대기 (Scheduler 재파싱)
2. UI **Code** 탭에서 새 코드가 반영됐는지 확인
3. Grid View에서 어제 행(2026-01-03) 헤더 클릭
4. 우측 패널 → **Clear (with downstream)**
5. **Failed**, **Past** 등 체크박스는 **모두 해제**, Downstream만
6. Confirm

> 같은 logical_date는 그대로 사용하고 Task만 다시 도는 형태. INSERT 같은 비-idempotent 코드라면 사전에 DELETE WHERE 또는 INSERT OVERWRITE 패턴인지 확인.

## 시나리오 3: 5일치 데이터를 한꺼번에 다시 계산

**상황**: 비즈니스 로직 변경. 2026-04-01 ~ 2026-04-05의 결과를 모두 새 로직으로 다시 만들고 싶다.

### 절차

```bash
# 1) 현재 상태 확인 (dry run)
docker compose exec airflow-scheduler \
  airflow dags backfill \
  --start-date 2026-04-01 \
  --end-date   2026-04-05 \
  --dry-run \
  04_backfill_demo

# 2) 기존 DAGRun을 지우고 새로 실행 (★ 운영 데이터 주의)
docker compose exec airflow-scheduler \
  airflow dags backfill \
  --start-date 2026-04-01 \
  --end-date   2026-04-05 \
  --reset-dagruns -y \
  04_backfill_demo
```

또는 UI Backfill 모달에서 **Reprocess Behavior = Completed** 선택.

### 후처리

- Grid View에서 5개 DAGRun이 모두 success로 마무리됐는지 확인
- 마트 테이블의 4/1~4/5 파티션이 새 값으로 들어갔는지 검증 쿼리 실행

## 시나리오 4: 누락된 며칠치 채우기 (장애 복구)

**상황**: 4/1~4/3은 정상, 4/4~4/5는 DAG가 깨져 DAGRun이 아예 안 만들어짐. 4/6 부터 다시 정상.

### 절차

```bash
docker compose exec airflow-scheduler \
  airflow dags backfill \
  --start-date 2026-04-04 \
  --end-date   2026-04-05 \
  04_backfill_demo
```

→ 이미 존재하는 다른 날짜 DAGRun은 건드리지 않고, 4/4와 4/5만 새로 만들어 실행.

## 시나리오 5: conf 받는 임시 파이프라인 1회 실행

**상황**: 운영 중 특정 사용자(user_id=42)에 대해서만 한 번 처리하고 싶다.

### 절차

UI:
1. ▶ → **Trigger DAG w/ config**
2. JSON: `{"target_user_id": 42}`
3. Trigger

CLI:
```bash
airflow dags trigger \
  -c '{"target_user_id":42}' \
  03_branching_example
```

DAG 코드 안에서:
```python
def main(**context):
    target = context["dag_run"].conf.get("target_user_id")
    if not target:
        raise ValueError("target_user_id required")
    process(target)
```

## 시나리오 6: 백필 도중 일부만 실패

**상황**: 7일치 백필 중 4/3과 4/5의 `fake_load`가 실패. 나머지는 success.

### 절차

```bash
# 실패한 것만 골라서 재시도
docker compose exec airflow-scheduler \
  airflow dags backfill \
  --start-date 2026-04-01 \
  --end-date   2026-04-07 \
  --rerun-failed-tasks \
  04_backfill_demo
```

→ 4/3, 4/5의 fake_load만 다시 시도. 다른 success Task는 건드리지 않음.

## 시나리오 7: 잘못 만들어진 DAGRun 삭제

**상황**: 실수로 future logical_date를 입력해 2030년 DAGRun이 생김.

### 절차

UI:
1. Grid View에서 2030 컬럼 헤더 클릭
2. 우측 패널 → **Delete DAG Run**

CLI:
```bash
airflow db cleanup --tables dag_run --dry-run    # 대량 정리 시
```

또는 메타DB 직접:
```sql
DELETE FROM dag_run
WHERE dag_id = '04_backfill_demo'
  AND logical_date = '2030-01-01 00:00:00+00';
```

## 시나리오 8: 로그가 안 보일 때

**상황**: Task 셀 클릭했는데 Logs 탭이 비어 있다.

### 점검

1. `logs/` 디렉토리 권한:
   ```bash
   docker compose exec airflow-scheduler ls -la /opt/airflow/logs/
   ```
2. Worker / Scheduler 컨테이너가 같은 logs 볼륨을 공유하는가? (compose 파일 확인)
3. Task가 정말 시작은 했는가? (state queued면 아직 로그 없음)
4. UI의 Try 번호가 여러 개라면 시도별 탭을 확인

## 시나리오 9: Pool로 외부 시스템 보호

**상황**: PostgreSQL 동시 연결 수가 제한적인데 백필 시 DAG가 한꺼번에 100개 쿼리를 던짐.

### 절차

1. Admin → Pools → **+ New**
   - Name: `postgres_etl`
   - Slots: `5`
2. DAG 코드 수정:
   ```python
   PostgresOperator(
       task_id="t",
       sql="...",
       pool="postgres_etl",
       pool_slots=1,
   )
   ```
3. 백필 다시 실행 → 동시 5개로 자동 제한

## 시나리오 10: 특정 시간대(KST) 기준으로 돌리고 싶다

**상황**: schedule이 KST 새벽 3시 기준이어야 한다.

### 방법 A: DAG의 timezone 설정

```python
import pendulum
from airflow import DAG
from datetime import datetime

local_tz = pendulum.timezone("Asia/Seoul")

with DAG(
    dag_id="kst_dag",
    start_date=datetime(2026, 1, 1, tzinfo=local_tz),
    schedule="0 3 * * *",   # KST 03:00 (start_date의 tz를 따름)
    catchup=False,
):
    ...
```

### 방법 B: cron을 UTC로 환산

```python
schedule="0 18 * * *"    # UTC 18:00 = KST 03:00 (다음날)
```

> **주의**: logical_date 자체는 항상 UTC로 메타DB에 저장됩니다. UI 표기만 timezone 토글로 바꿀 수 있을 뿐.
